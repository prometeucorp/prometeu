# Issue #148 Energy Use Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** Proposed plan. The budgets and interfaces below are implementation choices to validate, not current behavior.

**Goal:** Reduce Prometeu-owned background work and rendering cost while preserving active agents, transcripts, terminals, sharing, account isolation, and explicitly enabled PR monitoring.

**Architecture:** A small native activity context supplies window and power state to independent schedulers. Each feature owns its own refresh policy and effects; native provider/Git/GitHub access stays in Rust, and presentation avoids replacing unaffected DOM. Ship each area separately and compare it with a release-build baseline before proceeding.

**Tech Stack:** Tauri 2 and Rust, TypeScript/Vite, Vitest, Cargo tests, Playwright only where the E2E scope policy requires it, macOS Energy Log/Activity Monitor and `pmset` for native measurement.

**Spec:** [Issue #148](https://github.com/prometeucorp/prometeu/issues/148), at repository commit `b03e768`.

## Global Constraints

- The saved `prometeu:acordado` values `on`, `agent`, and `off` keep their present meaning. In particular, `agent` explicitly keeps the display awake while a local agent is working.
- `Status::Rodando` already includes native background children until they drain ([ADR 0056](../../decisions/0056-background-tasks-hold-completion.md)); do not infer activity from the person's workspace stage or the raw `turn.completed` event.
- Hidden or battery operation never stops an active agent, terminal, transcript pump, sharing, telemetry durability, or opt-in PR monitor. No relay/E2EE change is part of this issue.
- Provider payloads remain at the adapters. The `usage.json` map and per-account attribution remain compatible; a failed or missing reading is not zero usage.
- Any IPC or event shape change updates `src/ipc.ts`, the Rust handler, `src/mock.ts`, [IPC contract](../../contracts/ipc.md), and a compatibility or parity test. Visible copy uses both i18n catalogs. macOS and Linux behavior must be documented.
- Run focused tests first. Use `npm run check` after the cross-cutting implementation. Add browser E2E only for a concrete browser-dependent regression under the [scope policy](../../operations/development.md#e2e-scope).

## Review Focus

1. **A deleted account finishes an old quota probe:** its cache entry and identity must stay deleted. Task 3 adds a generation/removal test.
2. **A main turn ends with native children still running:** the `agent` and new system-only assertion must remain until the children drain. Task 2 tests the policy against `Rodando` and the existing `chat.rs` settlement tests.
3. **A Git mutation arrives during a slow scan:** one follow-up scan must run and its result must win; different repositories remain independent. Task 5 tests counted invocations with controlled timing.
4. **A hidden app returns after a long sampling gap:** the next CPU value and graph must not imply a continuous three-second interval. Task 4 tests elapsed deltas and gap handling.
5. **A slow general PR scan overlaps an explicit monitor:** general discovery must not erase known PRs, block monitor delivery, or start a model. Task 6 tests concurrency and the existing tracking rules.

## Verified Starting Point

| Area | Current path and behavior | Planning consequence |
| --- | --- | --- |
| Sleep | `src/statusbar.ts` derives one boolean from `on/agent/off`; `src-tauri/src/awake.rs` uses `caffeinate -d -i -s -w` for both active modes. | A quieter display policy requires an additional explicit choice, not migration of `agent`. |
| Quota | `src-tauri/src/usage.rs::watch` probes every registered profile sequentially, then sleeps 60 seconds. `antigravity.rs::discover` checks child completion every 20 ms. | Schedule by account and interest; keep live events and the last valid snapshot. `Agent.at` records a changed reading, so scheduler freshness needs separate runtime timestamps. |
| Resources | `src-tauri/src/machine.rs::watch` runs one `ps` every three seconds for the app lifetime; `src/statusbar.ts::showMachine` calls `draw`, which rebuilds every chip. | Change sample demand and DOM update separately, so each can be measured. |
| Git | `src/workspace.ts::draw` schedules `workspace_git_status` on every board redraw; Changes and `src/tree.ts` have separate five-second refreshes. `git.rs` builds full status with many Git commands. | Remove irrelevant invalidations first, then coalesce and reuse compatible repository snapshots without losing external edits. |
| PRs | `src/main.ts` invokes `refresh_prs` at startup and every minute; `github.rs` also has `pr_open`. `actions.rs` owns a separate opt-in monitor. | General discovery can slow down; the explicit monitor keeps its own promised interval and delivery. |
| Rendering | `chat.ts` coalesces events by animation frame, but `sync` computes pieces over the full timeline and repaints the growing Markdown block; `browser.ts` has a permanent body-wide mutation observer. | Profile WebKit before choosing a Markdown strategy; remove work whose output is provably unchanged. |

The issue's `top` sample, stack sample, and Git microbenchmark establish candidates, not watts or a dominant battery contributor. Do not set a battery-life target from them.

## Proposed Freshness Budgets

These are starting values for the baseline/profiling gate. “Foreground” means the native window is visible and focused. Unknown power uses the battery budget for discretionary work. Return to foreground or opening the relevant panel dispatches a stale refresh immediately; provider/network completion remains bounded by its own timeout.

| Work | Foreground on AC | Foreground on battery | Hidden/minimized/unfocused |
| --- | --- | --- | --- |
| Selected account quota | 60 s | 120 s | 15 min; live provider events still apply |
| Other registered account quota | 10 min | 20 min | 30 min |
| Compact resource chip | 15 s | 30 s | no detailed `ps`; refresh on return |
| Open resource panel | 3 s | 5 s | panel closes or suspends sampling |
| General PR discovery | 3 min | 5 min | 15 min; opt-in tracking unchanged |
| Visible Changes fallback | 5 s | 10 s | no scan; refresh on return |
| Visible Files marks fallback | 15 s | 30 s | no scan; refresh on return |

An account-panel open or account switch queues an immediate probe only if its last *attempt* is older than 30 seconds. A failed probe backs off per account at 1, 2, 5, 15, then 30 minutes, capped at 30 minutes; explicit selection/login may wake it sooner. Visible selected quotas also schedule at a known reset boundary when that is sooner than the normal interval. Native Git mutations and saved files invalidate immediately. If a watcher proves reliable and cheaper, extend visible Git fallback to 30 seconds; otherwise retain the table above. These values should be revised with recorded measurements, not silently changed during implementation.

## Task 2: Offer System-Only Sleep Inhibition Without Reinterpreting Saved Choices

- [ ] Write the saved-preference compatibility tests and native command tests first: old `agent` retains display assertion; `agent-system` omits it; repeated state is a no-op; last agent settlement, mode change, normal exit, and unexpected app termination release the assertion. - [ ] Implement explicit inhibitor transitions. - [ ] Add the new menu label/hint through i18n and preserve the old localStorage key and values. Explicitly stop the inhibitor during the native exit path while keeping PID-tied cleanup for crashes.
- [ ] Run `cargo test awake`, the focused policy tests, `npm run typecheck`, and a native release-build manual assertion check. Update the ADR and contracts with the chosen behavior. Commit as `feat(app): allow display sleep during active agents`.

## Task 3: Schedule Quota Probes Per Account and Remove Short Child Polling

**Files:** Extract scheduling from `src-tauri/src/usage.rs` into `src-tauri/src/usage_scheduler.rs` with clock/effect tests; modify `src-tauri/src/antigravity.rs`, `src-tauri/src/accounts.rs`, `src/statusbar.ts`, `src/accounts.ts`, `src/ipc.ts`, `src/mock.ts`; update `docs/contracts/accounts.md`, `docs/contracts/ipc.md`, and `docs/quality/provider-matrix.md`.

**Interface:** `usage_refresh({ provider?: ProviderId }) -> void` marks registered profiles for a bounded immediate attempt; it never returns credentials or blocks the UI. Scheduler state tracks `next_due`, `last_attempt`, failure count, and account generation separately from persisted `Agent.at`.

- [ ] Write controlled-clock tests for selected/inactive/battery/hidden budgets, a reset boundary, failure backoff, live event precedence, login pause, selection wake, and a removed account whose old probe finishes late. Count provider process launches, not only resulting `usage` events.
- [ ] Replace the sequential all-profile loop with per-account due work; allow only one probe per account, check account generation before publishing identity or quota, and preserve the last valid reading on failure. Avoid probes when the provider has no registered profile.
- [ ] Let the account UI request a stale refresh; use live Claude/Codex events where available. Reuse a Codex connection only after proving that its account and protocol lifetime match the captured profile; otherwise keep the bounded separate probe.
- [ ] Replace Antigravity's 20 ms completion loop with an exit notification/wait and a ten-second deadline, preserving stdout draining, timeout kill, and process reap. Test success, hung child, and cancellation/removal paths.
- [ ] Run `cargo test usage`, `cargo test antigravity`, focused account tests, `npm run typecheck`, and native launch-count comparison. Update the provider matrix's differing quota paths. Commit as `perf(accounts): budget quota probes by account interest`.

## Task 5: Coalesce Git Status Work and Invalidate It Precisely

**Files:** Modify `src/workspace.ts`, `src/tree.ts`, `src-tauri/src/session/git.rs`, `src-tauri/src/session/git_tests.rs`; add a focused single-flight unit where the Git command runner can be counted; update `docs/contracts/git.md` and `docs/quality/energy-profile.md`.

**Interface:** Existing `workspace_git_status` and `tree_git_status` IPC shapes remain. Within Rust, a per-worktree status service owns one in-flight computation, a dirty generation, the last compatible raw porcelain snapshot, and a bounded fallback; project-only tree roots retain their own path semantics.

- [ ] Test that unrelated board/chat updates do not call `workspace_git_status`; workspace switch, repository-list change, saved file, Git mutation, focus return, and visible fallback do. Include an external edit without an app event.
- [ ] Add a counted concurrent-scan test: two consumers of one worktree share work, an invalidation during the scan produces exactly one follow-up, and a second repository runs independently. A stale result must never overwrite the follow-up.
- [ ] Remove unconditional status scheduling from `workspace.draw`. Coalesce Changes and Files consumers; derive tree marks from the same compatible porcelain data while preserving `AD`, conflicts, ignored/untracked paths, grouping-folder prefixes, index fingerprint, branch/upstream metadata, and per-repository errors. Do not hold the mutation lock while waiting for a scan.
- [ ] Benchmark a bounded filesystem/Git watcher on macOS and Linux against the fallback. Adopt it only if it catches external worktree, resolved gitdir/index, branch and commit changes without higher idle cost; otherwise keep the visible fallback budgets above and record why the watcher was deferred.
- [ ] Run real-repository `cargo test session::git_tests`, focused tree/Changes tests, `npm run typecheck`, and a native Git-process count with multi-repository workspaces. Commit as `perf(git): coalesce workspace status refreshes`.

## Shipping Order and Decision Gates

1. Task 0 is a prerequisite for every performance claim. Task 1 supplies context for Tasks 3–6. Task 2 can proceed independently after Task 0. Tasks 3–6 can be reviewed and shipped as separate PRs after Task 1. Task 7 depends on its own profile, not on the polling work.
2. After each PR, compare its controlled scenario with the baseline and check freshness/correctness. Keep an optimization only if it reduces relevant work without unacceptable freshness or interaction regressions.
3. The first acceptance target is deterministic: hidden idle starts no detailed `ps` or Git scans, account and general-PR attempts respect their budgets, changed machine values do not rebuild unrelated chips, and returning to the app queues the relevant refresh. Energy/discharge improvement is a measured outcome, not an assumed acceptance number.
